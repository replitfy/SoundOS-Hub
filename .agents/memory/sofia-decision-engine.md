---
name: Sofia decision engine (motor de decisão)
description: Durable rule for the decision_run/eligibility audit engine — what counts as evidence.
---

- Eligibility (module prerequisites Água→Fogo→Ar→Terra) must be computed only from curated structured columns — currently just the two legacy presencial flags — never from free-text fields (e.g. `pessoa_participacoes.curso` has no canonical values yet) and never from what the person merely claims in chat. **Why:** a false "elegível" from a word-matched free-text field is worse than a false "bloqueado"; the whole point of the `decision_run` audit is that eligibility can't be talked around by the person, rubber-stamped by the LLM, or accidentally granted by an unrelated text match. **How to apply:** any new signal source wired into module-completion detection must be a real, controlled completion record — not raw conversation text or unnormalized imported text fields; every eligibility decision_run must also snapshot the exact structured fields it evaluated, since eligibility evidence is only auditable if it survives later edits to the pessoa record.
- Reducing audit noise is a *presentation* change only: never stop recording, cache, or skip the per-decision eligibility snapshot to make the log quieter. Absent state ("no completion on file") is itself the fact that produced a block, and the check must re-run every turn because a module can enter the conversation at any point. **Why:** eligibility is genuinely evaluated on only ~2% of turns, which makes the recorded snapshot look redundant and invites "just check it once per session" — but skipping it reintroduces the false-"elegível" risk the engine exists to prevent, and dropping the empty record makes a later ficha edit silently rewrite history. **How to apply:** hide it in the UI when it says nothing (nothing completed *and* eligibility not evaluated); keep writing it always.
- Free-text detection needs different rules depending on whose text it is: a human's raw message can be about anything (needs a domain-anchor word alongside the module name to avoid false positives like "ar condicionado"), but the bot's own generated response is already domain-constrained by its system prompt, so bare module-name matching there (no anchor) is the safer choice — an anchor requirement on generated output lets bypasses like "você pode fazer Fogo" slip through. **Why:** reviewers rejected both extremes — anchorless matching on user input (false positives) and anchor-required matching on generated output (bypasses) — before this distinction was made explicit.
- A gate that blocks a *tool call* is not sufficient on its own: the model can still describe/offer the same gated thing in the surrounding free text (before, after, or instead of the tool call), and it can spontaneously offer it with no tool call and no user mention at all. **Why:** three separate review rounds each found a different path around a tool-only gate. **How to apply:** for any hard constraint like this, gate the actual outgoing text before it reaches the client (buffer + check + substitute if needed), not just the tool arguments or the user's input.
